## ⚡ 성능 개선

## 1. 캘린더 대량 데이터 렌더링 성능 개선

### 문제

DB에 약 **100,000개 이상의 일정 데이터**가 존재하는 환경에서 성능을 테스트했다.

API 조회 성능은 비교적 빠른 편이었다.

| 단계 | 처리 시간 |
|-----|----------|
| API 조회 | 약 200ms |
| 프론트 렌더링 | 약 40,000ms |

**문제는 API가 아니라 프론트엔드 렌더링 과정**이었다.

---

### 원인 분석

캘린더는 월 단위로 화면을 렌더링하며  
일정 조회 시 `start ~ end` 기간을 서버에 전달하여 해당 범위의 이벤트만 가져온다.

단일 일정은 해당 날짜 셀에 바로 표시할 수 있지만  
기간 일정의 경우 여러 날짜에 걸쳐 **하나의 이벤트 바(event bar)**로 표시되어야 한다.

이를 위해 각 이벤트에 대해 다음 계산이 필요하다.

- 이벤트가 **어느 주(week)에 속하는지**
- 해당 주에서 **몇 번째 칸부터 시작하는지**
- **몇 칸까지 이어지는지**

기존 구현에서는 이러한 계산을 캘린더 렌더링 과정에서 수행했다.

```typescript
events.map(...)
→ splitEventByWeek(...)
→ 각 주차 렌더링 시 모든 이벤트 다시 검사
```

이 구조에서는 **각 주차 렌더링 시 전체 이벤트 데이터를 반복 검사**하게 된다.

즉 렌더링 과정에서

> week 수 × 전체 이벤트 수


만큼의 반복 계산이 발생하면서 렌더링 시간이 크게 증가했다.

---

### 해결

다음과 같은 방식으로 렌더링 구조를 개선했다.

1️⃣ 이벤트를 **주 단위로 분할하는 렌더링 구조** 적용

```
event
 → splitEventByWeek
 → week 단위 이벤트 그룹 생성
 → 필요한 주만 렌더링
```

이 방식으로 이벤트 계산 범위를 **해당 주 단위로 제한**했다.

2️⃣ **이벤트 캐싱 구조 적용**

캘린더 렌더링 시 계산된 이벤트 바 데이터를 캐시에 저장했다.

- 일정 조회 시 캐시 사용
- 일정 **추가 / 수정 / 삭제 시 캐시 갱신**

이를 통해 불필요한 계산을 줄였다.

---

### 결과

API 응답 이후 이벤트 데이터를 상태에 반영한 시점부터
캘린더 렌더링이 완료될 때까지의 시간을 측정했다.

| 항목 | 개선 전 | 개선 후 |
|----|----|----|
| 렌더링 시간 | 약 40,000ms | 약 183ms |

일정 데이터가 많은 환경에서도 캘린더 렌더링 시간이 크게 감소한 것을 확인했다.

## 2. 일정 조회 API 인덱스 적용

### 문제

일정 조회 API는 다음 조건을 기반으로 데이터를 조회한다.

```postgresql
WHERE calendarId = ?
AND start BETWEEN ? AND ?
```

초기에는 `calendarId` 단일 인덱스만 존재했다.

대량 데이터 환경에서 `start` 조건을 함께 사용하는 조회 패턴에 대해  
효율적인 인덱스 구조가 아니었다.

---

### 원인 분석

기존 인덱스 구조

```
INDEX (calendarId)
```

이 경우 데이터베이스는 먼저 `calendarId`에 해당하는 모든 이벤트를 찾은 뒤  
그 결과에서 `start` 조건을 다시 검사해야 한다.

즉, 캘린더에 저장된 이벤트 수가 많을수록 불필요한 데이터 탐색이 발생할 수 있었다.

---

### 해결

일정 조회 쿼리는 다음 조건을 기반으로 동작한다.

```
WHERE calendarId = ?
AND start <= :rangeEnd
AND end >= :rangeStart
```

인덱스 활용 흐름은 다음과 같다.

1️⃣ `calendarId`로 먼저 캘린더 범위를 좁힘  
2️⃣ `start <= rangeEnd` 조건으로 범위 탐색  
3️⃣ 이후 `end >= rangeStart` 조건을 추가 필터링

이러한 조회 패턴을 고려했을 때  
`calendarId` 이후 **범위 조건으로 사용되는 컬럼이 `start`**이므로  
다음과 같은 복합 인덱스를 적용했다.

```
CREATE INDEX idx_event_calendar_start
ON event (calendarId, start);
```

`start` 이후에 `end` 컬럼을 추가하는 방법도 고려했지만  
이미 `start`에서 범위 조건이 사용되기 때문에  
추가 컬럼이 인덱스 활용도에 큰 영향을 주지 않을 것으로 판단했다.

따라서 `(calendarId, start)` 구조가  
조회 패턴에 가장 적합한 인덱스라고 판단하여 적용했다.

---

### 결과

DB에 **100,000개 이상의 일정 데이터**를 생성한 후  
일정 조회 API의 응답 시간을 측정했다.

| 항목 | 개선 전 | 개선 후 |
|----|----|----|
| 조회 시간 | 약 93ms | 약 87ms |

조회 패턴에 맞게 인덱스를 구성하여  
대량 데이터 환경에서도 안정적인 일정 조회 성능을 유지하도록 개선했다.

## 3. API 동시 요청 테스트

이벤트 생성 API의 동시 요청 처리 능력을 확인하기 위해 테스트를 진행했다.

### 테스트 조건

- 동시 요청 수 : **100 requests**
- 비동기 요청을 동시에 전송하여 API의 동시 처리 능력 확인

### 결과

| 요청 수 | 실행 시간 |
|-------|----------|
| 100 | 약 111ms |

100개의 요청이 모두 정상적으로 처리되는 것을 확인했다.

동시 요청 환경에서도 이벤트 생성 API가 안정적으로 동작하는 것을 확인했다.
